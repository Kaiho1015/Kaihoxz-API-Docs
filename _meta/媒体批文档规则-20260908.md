## 0. 这一批要做什么

网关这轮把 APIMart 的媒体模型全量重配了一遍（参数按上游合同全开、计费维度补齐、逐组付费连通），
目录里**启用且有路由**的媒体组现在是 92 个。文档要做到：

1. **每个启用组都有页可查**，每个字都能在目录里找到出处（参数 / 动作 / 约束 / 计费维度）。
2. **停用的组从页面上消失**（模型表、卡片、示例里都不留），但页面文件本身不删。
3. cn / en 两版**结构、模型 ID、数字逐项一致**。

真相源只有一个：**`go/catalog/families/<family>.json`**（配置即代码，线上就是它 apply 的结果）。
不要再去查后台接口、不要拿旧页面当依据、不要凭记忆写。

## 3. 计费小节：媒体类的形状（补 SOP §5）

只写**维度与口径**，不写数字。按 `price_config` 的键判断形状，一个组可能同时命中多条：

| `price_config` 里有 | 口径（写法） |
|---|---|
| `video_prices` + `per_second: true`，键是 `720p` / `1080p` / `4k` 这类分辨率 | **按分辨率档 × 秒数**计费；时长取请求的 `duration` |
| `video_prices` 键是 `720p_5s` / `1080p_10s` 这类 | **按分辨率 × 时长档的整片价**，不按秒 |
| `video_prices` 里有 `<res>_video_ref` | 带参考视频（`video_urls`）时，**输出秒**改按参考档单价计（没配这个键就仍按基础档），参考视频本身的秒数不计 |
| `video_prices` 里有 `<res>_video_input_second` | 参考视频的**输入秒数另计一笔**（输出秒照常收）；探不到时长按 `max_video_input_seconds` 计。若同时 `input_video_replaces_output: true`，输出侧不收，只收参考视频秒数（Omni-Flash-Ext） |
| `video_prices` 里有 `sound` / `<res>_sound` 之类 | 开启音频生成（`generate_audio` 等）走带声档 |
| `video_prices` / `image_prices` 里有 `ref_image` 或 `<res>_ref_image` | 每张参考图**另计一笔**，按张 |
| `image_prices` 键是 `1k` / `2k` / `4k` 或尺寸 | **按成功出图的固定张价**，分辨率是唯一维度；`default` 是未命中分辨率键时的兜底，要写 |
| `image_usage_rates`（多半配 `settlement`） | **按实际 token 用量结算**：提交时按预估用量冻结，完成后按实际用量结算退差；维度 = 文本输入 / 图片输入 / 图片输出（有缓存键才写缓存） |
| `settlement: {basis: upstream_cost}` 单独出现在视频组 | 提交时按时长上限冻结，完成后**按实际生成结果结算退差**（不写「上游实付」「markup」这些内部词） |
| `audio_prices` 按动作分键（Suno / Flow Music） | **按次计费，不同动作价格不同**；列出哪些动作是「一次一价」 |
| `per_character` | 按**输入文本字符数**计费，不收输出费 |
| `per_minute` | 按**音频分钟数**计费（不足一分钟怎么算不知道就不写） |
| `duration_special` = `model_chosen` | 这个组/动作**不传 `duration`**，时长由模型决定；冻结按该组声明的时长上限 |
| `duration_special` = `source_length` | `duration: 0` 表示保留源素材时长 |

每个「计费」小节固定收尾三句（SOP §5 原文）：只有成功才计费 / 失败取消全额退款 / `cost` 是整数 quota（500,000 quota = 1 USD），外加实时价指引 `<Note>` 块。

## 4. 链式动作（`ref_task_id`）

Suno 的 extend / cover 等、Midjourney 的 upscale / variation 等、MiniMax H3 Regeneration、Seedance 2.5 的 extend / edit、Veo 逆向版 extend：
凡 `supported_common_params` 里有 `ref_task_id` 的组，链式动作的写法是**传上一步我方的 `task_id`**（不是上游的 id）。
页面上写一段「接着往下做」：先 `imagine` 拿到 `task_id`，再 `upscale` 时带 `ref_task_id`。
哪些动作需要 `ref_task_id`、哪些不需要（如 MJ 的 blend / describe），看 `constraints`。

## 5. 停用组怎么处理

- 组 `enable: false`（或没有 `status: 1` 的路由）：从该页的模型表 / 卡片 / 示例 / 参数说明里**删掉**，不写「已下架」「即将」（changelog 才记事件）。
- 整页所有组都停用（例：`image/imagen.mdx`）：页面留、导航摘、页顶加 `<Warning>` 说明已下架并指向替代页——这是既有套路，本批只有 Imagen 一例，已由整合者处理，写手不用管。
- 已经在 `changelog/models.mdx` 记过下架的不再重复记。

## 6. cn / en 两版

- 同一页同一结构：小节顺序、表格行数、ParamField 顺序、示例数量一致。
- 模型 ID、参数名、取值、数字、示例请求体逐项相同；只有散文和表头翻译。
- `constraints` 中文用 `message_i18n.zh` 原文、英文用 `.en` 原文。
- 英文页链接指向 `/en/...`，中文指向 `/cn/...`。
- 中文全角标点、英文半角；小数 / 版本号 / URL / 代码保持半角。

## 7. 分工与交付协议（子代理）

写手只写自己名下家族的页面（cn + en），**不动**：`docs.json`、各模态 `overview.mdx`、`changelog/*`、`index.mdx`、`docs/models.mdx`、别人的家族页。
这些由整合者统一改。写手交付时返回一份清单：

1. 新建 / 修改的文件（相对路径）
2. 需要挂进 `docs.json` 的页面路径与侧边栏标签（cn / en 各一份；是否需要 `group` + `root`；需要的 `redirects`）
3. 给 `changelog/models.mdx` 的一条合并条目（cn / en 各一段，不带价格）
4. 页面里出现的模型 ID 全集（供整合者核对目录）
5. 没把握、故意没写的点（列出来，不要猜着写进页面）

写手动手前先跑：`git status` 确认在分支 `docs/media-batch-20260908`；写完自查 SOP §6 的 checklist（黑话 grep、`$` 脚本）。
不 commit，不 push，不改分支——整合者统一提交。
